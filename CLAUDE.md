# azvms.info — project constitution

Read this before exploring the codebase — it should cover what you need without re-deriving it. Update it whenever you make a change future sessions would otherwise need to rediscover.

## What this is

A static web app that compares Azure VM sizes/SKUs side by side — technical specs (vCPUs, memory, IOPS, throughput, NICs, GPU, encryption/networking support, etc.) *and* pricing, filterable by minimum requirements. Forked from the archived `azure-instances.info` (itself a fork of `ec2instances.info`). See [README.md](README.md) for the full "why."

Live site is deployed via **Azure Static Web Apps**. Owner/repo: `antnorwe/azvms.info`.

## Architecture

- **`web/`** — the entire static site. No build step, no framework. Plain HTML/CSS/JS + jQuery + DataTables (loaded from CDN in `index.html`).
  - [web/index.html](web/index.html) — the page. A big `<table id="data">` driven by DataTables: filters, region/cost-duration/column-visibility dropdowns, compare mode, CSV export.
  - [web/default.js](web/default.js) — all client logic: builds the DataTable from `azure.json`, applies filters, redraws costs on region/duration change, persists UI state via `store/store.js` (localStorage wrapper). `generate_data_table()` builds each row as a plain positional array (`row[N] = ...`) that must line up exactly with `index.html`'s `<thead>` column order - see "Hard-won lessons" before touching column indices.
  - [web/azure.json](web/azure.json) — the VM dataset. Large (500KB+). One entry per SKU name, each with `spec`, `zones` (per-region availability), and `standard`/`lowpriority` pricing broken out by OS and term. Regenerated by the data pipeline (see below) — **never hand-edit this file**.
  - [web/lastupdate.json](web/lastupdate.json) — `{"lastUpdateTime": "..."}`, the single source of truth for the "Last Update" text shown in the header/footer. Also written by the data pipeline. **Never hand-edit, and never hardcode a date anywhere else in the page** — see "Hard-won lessons" below.
  - [web/disks/index.html](web/disks/index.html) + [web/disks/default.js](web/disks/default.js) — the **Disks** tab, a second DataTables page for Managed Disk SKUs, structurally mirroring the VM page but standalone (own JS, no shared state with `default.js` beyond `store/store.js` and a distinct `disk_settings` localStorage key so the two pages' filters don't clobber each other). Reads `../azure.json`'s sibling, `web/disks.json`. Handles the Premium/Standard/StandardSSD (single fixed monthly price) vs PremiumV2/UltraSSD (three provisioned-unit meters: capacity/IOPS/throughput) shape difference by leaving the inapplicable price columns blank per row, same convention the VM table uses for GPU columns.
  - [web/disks.json](web/disks.json) — the disk dataset, same shape/regeneration story as `azure.json` (written by `GenerateDiskResourceJson.ps1`, never hand-edit). Keyed by `"<sizeCode>_<redundancy>"` (e.g. `P10_LRS`) since a size can have multiple redundancy variants, each `{"specs": {...}, "prices": [<raw Retail Prices API items>]}` — prices are kept as the raw API array (not normalized into a region map like `azure.json` does) and filtered client-side by `armRegionName`/`type` in `disks/default.js`.
  - [web/staticwebapp.config.json](web/staticwebapp.config.json) — marks `azure.json`, `disks.json`, and `lastupdate.json` as `Cache-Control: no-cache` at the CDN edge, since all three change daily via automation.
  - [web/bc/](web/bc/) and [web/rds/](web/rds/), [web/default.old](web/default.old) — **unused leftovers from the original upstream fork** (still branded "EC2 Instance Comparison" / "Amazon EC2"). Not linked from the live nav (the RDS tab is commented out in `index.html`). Don't assume these are live or maintained; ignore unless someone explicitly asks to revive them.
  - [web/bootstrap/](web/bootstrap/), [web/datatables/](web/datatables/) — vendored third-party assets.

- **No backend API.** There used to be an Azure Functions app under `api/` (a single `get-lastupdatetime` endpoint) — it never worked reliably and was removed entirely. Don't recreate a Functions app for this without discussing it first; the static-JSON-file approach below replaced its purpose.

- **Data pipeline** ([scripts/](scripts/)):
  - [scripts/Common.ps1](scripts/Common.ps1) — dot-sourced (`. "$PSScriptRoot\Common.ps1"`) by both generation scripts below. Holds `Connect-AzIfNeeded` (non-interactive-friendly auth), `Invoke-RestMethodWithRetry` (429 retry/backoff, optional `-ResponseHeaders ([ref]$var)` to capture response headers), and `Get-AllRetailPrices -Filter <odata filter>` (pages through a Retail Prices API query via `NextPageLink`, throttling proactively off the API's own `x-ms-ratelimit-remaining-retailPrices-requests`/`x-ms-ratelimit-retailPrices-retry-after` response headers). Add any future shared logic here rather than duplicating between the two scripts.
  - [scripts/GenerateVMResourceJson.ps1](scripts/GenerateVMResourceJson.ps1) — calls the ARM `Microsoft.Compute/skus` API (needs an authenticated Az context) for VM capabilities, then **one bulk `Get-AllRetailPrices` call** (`serviceFamily eq 'Compute' and serviceName eq 'Virtual Machines'`, no per-SKU filter) grouped in-memory by `armSkuName` into a hashtable, so the per-SKU loop is a lookup, not an HTTP call. Writes `web/azure.json` and `web/lastupdate.json` (UTC timestamp of the run).
  - [scripts/GenerateDiskResourceJson.ps1](scripts/GenerateDiskResourceJson.ps1) — same ARM shape for Managed Disk specs (`resourceType eq 'disks'`), same bulk-then-lookup pricing approach: one `Get-AllRetailPrices` call using `contains(productName, ...)` to cover every disk tier (fixed Premium/Standard/StandardSSD plus provisioned-unit PremiumV2/UltraSSD) without pulling in unrelated Storage products, grouped by `"<skuName>|<meterName>"`. Writes `web/disks.json`. One entry per (size, redundancy) combo — the `Group-Object name | foreach-object { ... }` inner loop matters: it used to only keep the *last* redundancy variant per size (an `Add-Member` placed outside that loop overwrote earlier ones), so if you touch this script keep the `Add-Member` call inside the per-group loop.
  - **Why bulk fetching, not just faster per-call code**: the Retail Prices API rate-limits by *request count* (its own headers show roughly 10 requests/60s), not by data volume or client speed - a single unfiltered SKU query already returns hundreds of rows in one response (no per-request row cap that scales down with narrower filters), so replacing ~400 per-SKU calls with ~1 bulk paginated fetch (dozens of pages, not hundreds of round-trips) is what actually fixes the runtime. A language rewrite wouldn't have helped: the bottleneck was architecture (call count), not execution speed.
  - Both scripts are run in sequence by `update-vm-data.yml`. The ARM capabilities call needs real Azure credentials (no Azure access from an agent session, so that part can't be tested live), **but the Retail Prices API is public/unauthenticated** and can be curled or called from `Get-AllRetailPrices` directly to validate pricing-fetch changes before they ever reach CI - do this for any change to the price-fetching logic. When testing the frontend against generated data, hand-craft a small temporary `web/*.json` fixture, verify via the local preview (see "Local development" below), then **delete the fixture before committing** — never let fabricated data reach `web/azure.json`/`web/disks.json` in git.

- **CI/CD** ([.github/workflows/](.github/workflows/)):
  - [azure-static-web-apps-happy-tree-030096503.yml](.github/workflows/azure-static-web-apps-happy-tree-030096503.yml) — deploys `web/` to Azure Static Web Apps on push to `main`, PR previews, and `workflow_dispatch` (see below). `app_location: ./web`, no `api_location` (see above).
  - [update-vm-data.yml](.github/workflows/update-vm-data.yml) — named "Refresh Azure Pricing Data". Scheduled (daily 05:17 UTC — deliberately off the hour, see "Hard-won lessons") + manual (`workflow_dispatch`) job that logs into Azure via **OIDC** (no stored secret), runs `GenerateVMResourceJson.ps1` then `GenerateDiskResourceJson.ps1`, and pushes to `main` if `web/azure.json`/`web/disks.json`/`web/lastupdate.json` changed. It then explicitly dispatches the deploy workflow above via `gh workflow run` — see "Hard-won lessons" for why that push alone doesn't trigger it. Requires repo secrets `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID` and an Azure AD app registration with a federated credential trusting `repo:antnorwe/azvms.info:ref:refs/heads/main`, holding at least `Reader` on the subscription. Also requires Actions "Read and write permissions" enabled in repo settings (for the push step).

## Roadmap

The user asked for these, in this order, as value-add improvements — implement in sequence unless told otherwise:

1. ~~Disk metrics as a separate "Disks" tab/table~~ — done (`web/disks/`).
2. ~~Cost-per-vCPU / cost-per-GB-RAM computed columns on the VM table~~ — done (`format_cost_per_unit()` in `default.js`, columns 22/23, based on Linux on-demand hourly cost).
3. ~~Shareable filtered views~~ — done. Fixed a real bug in the VM page's existing (pre-fork) machinery: `apply_minmax_values()` called `change_region(g_settings_defaults.region)` instead of `g_settings.region`, so a region from a shared URL/localStorage was loaded into settings correctly but then immediately overwritten back to the hardcoded default before render - meaning region (and, since `change_region()` cascades into `change_cost()`, cost_duration too) never actually restored from a link. Also neither page's `url_for_selections()`/`maybe_update_url()` encoded values at all (`encodeURIComponent`), nor decoded them on the read side - a search term with `&`, `%`, `#`, or a space would silently corrupt the query string or fail to round-trip. Fixed both, on both pages.
4. Combined VM+disk cost estimate — pick a VM row and a disk row, show a realistic combined monthly estimate. Depends on #1 being in place, which it now is.

## Hard-won lessons (don't repeat these)

- **`reserved_term`/`#reserved-term-dropdown` is a fully vestigial setting on the VM page** - `g_settings`, `g_settings_defaults`, `url_for_selections()`, and `change_reserved_term()` all reference it, but `index.html` has no `#reserved-term-dropdown` element at all (confirmed by grep), and `generate_data_table()` doesn't use `reserved_term` to select between the 1yr/3yr columns it computes - both are always shown regardless of this setting's value. `change_reserved_term()` no-ops harmlessly on the missing element (jQuery doesn't error on an empty selector) rather than doing anything. Don't spend time trying to "fix" its dropdown not updating - there's no dropdown to update. If you ever want this feature for real, it needs actual UI markup added first.

- **Changing a DataTable's column count breaks existing visitors via `stateSave` - and not always loudly.** Both `#data` tables use `bStateSave: true`, which persists column order/visibility/search state to `localStorage` keyed (by default) on the page path - not on the column layout. A visitor whose browser still has state saved from before a column was added/removed gets DataTables applying that now-incompatible state, and it has (at least) two different failure modes, both confirmed by reproducing them directly (via the local preview, temporarily swapping in the old/new `default.js`+`index.html` pairs from git history and carrying the *same* `localStorage` state between them): (1) an outright error (`DataTables warning: ... Requested unknown parameter 'N' for row X, column N`), or (2) worse, **silent data corruption with no error at all** - DataTables truncates its internal column model to match the stale (shorter) `columns[]` state array and everything after the insertion point shifts, so a column can display a completely different, wrong field's data (e.g. a new "Cost per vCPU" column silently rendering an unrelated boolean column's `True`/`False` values instead of erroring). Don't assume "no console error" means state restoration is safe. Fixed by overriding `stateSaveCallback`/`stateLoadCallback` to key the storage on the *current* `<thead>` column count (`'DataTables_..._cols' + $('#data thead tr:eq(0) th').length`) instead of DataTables' default page-path key - any future column-count change on either table automatically starts every visitor fresh instead of restoring incompatible state, with no version number to remember to bump. To verify a fix like this, don't just check a normal load with an already-consistent cache - reproduce the actual failure first (plant a realistic stale state under the *old* default key, e.g. by generating it against the pre-change code and carrying it forward) and confirm both the header labels *and* the row values at the affected positions are correct, not just that no error was thrown.
- **`generate_data_table()`'s `row[N]` indices are positionally coupled to `index.html`'s `<thead>` column order** - there's no naming, just a long hand-numbered sequence, and `row.slice(1)` at the end drops index 0 (used for the row's tooltip/description text, not a real column) before the array is handed to DataTables. Inserting a new column in the middle means renumbering every subsequent `row[N] =` assignment (not just appending at the end) - `Add-Member`-in-a-loop-style bugs are easy to introduce here. **Verify with `table.columns().header()` cross-referenced against `table.row(i).data()` in the browser console** (via the local preview), not by scraping `<th>` text with jQuery - hidden columns' `<th>` elements can be absent from a naive DOM query, silently misaligning a manual header-to-value check even when the actual table is fine. Also verify sorting with `table.rows({order:'current'}).data()`, not `table.row(i, {order:'current'})` - a plain integer row selector ignores the `order` option entirely and just returns that row's fixed original-data-order position.
- **Never hardcode a date/timestamp anywhere in `index.html`.** Someone used to hand-edit the "Last Update" spans on every manual refresh; that habit caused a real bug where the page would flash the correct value (from `lastupdate.json`) then get overwritten by a stale hardcoded one, or vice versa. The header/footer spans should only ever contain a neutral placeholder (`Loading...`) — `default.js`'s `loadLastUpdateTime()` is the only thing that should ever set their text.
- **Fetch `azure.json` and `lastupdate.json` without caching** (`fetch(..., { cache: 'no-store' })` / jQuery `cache: false`). They're regenerated daily; stale browser/CDN caching of them has caused real user-visible bugs. `staticwebapp.config.json` backs this up at the CDN edge — keep both in sync if you touch either file's serving path.
- **The Azure Retail Prices API rate-limits by request count, not data volume** (`429 Too many requests`, roughly 10 requests/60s per its own `x-ms-ratelimit-remaining-retailPrices-requests`/`x-ms-ratelimit-retailPrices-retry-after` response headers). The original fix was a 1s pace between ~400 per-SKU calls, which just meant hitting the same wall slower (~40 min minimum, dominated by 429 backoff). The real fix was cutting total requests: `Get-AllRetailPrices` in `Common.ps1` bulk-fetches everything for a broad filter in a handful of paginated calls, grouped in-memory afterward - both generation scripts now do zero per-SKU network calls in their main loops. If you add a new API integration to this pipeline, check the response headers for a documented rate limit before assuming a fixed delay is the right throttle.
- **`Write-Output` inside a PowerShell function pollutes its return value** — it feeds the same success-output pipeline the function returns, so any progress/logging line written with `Write-Output` (or unsuppressed bare output) inside a function gets spliced into whatever the caller receives, silently corrupting collections. This bit `Get-AllRetailPrices` during development (string log lines ended up mixed into the returned price array) - use `Write-Host` for progress messages inside a function that returns data via the pipeline.
- **The Retail Prices API's `$skip`-based pagination can return the same row twice across a page boundary.** Confirmed directly against the live API (same `meterId`/`armRegionName`/`armSkuName` on both sides of a boundary), most likely because it's a live, periodically-reindexed dataset rather than a static snapshot - not reliably reproducible on demand, but real. This matters because neither generation script's `Add-Member -MemberType NoteProperty` calls use `-Force`, so a genuine duplicate throws a terminating "member already exists" error - a latent risk that bulk pagination (hundreds of page boundaries per run) makes much more likely to actually hit than the old per-SKU approach ever was. `Get-AllRetailPrices` now dedupes every page's items before returning them. **`meterId` alone is not a safe dedup key** - it's shared across `type` variants (`Consumption`/`DevTestConsumption`/`Reservation`) for the same underlying meter, so dedup on a compound key (`region|type|skuName|reservationTerm|meterId`) instead, or you'll silently merge genuinely different price rows.
- **A `git push` made with `GITHUB_TOKEN` inside a workflow does not trigger other workflows' `push` events** (GitHub blocks this deliberately to prevent recursive runs) — confirmed by checking the deploy workflow's run history: no `push`-triggered run ever corresponded to a commit `update-vm-data.yml` made itself. `workflow_dispatch` and `repository_dispatch` are explicitly exempt from this restriction, so `update-vm-data.yml` dispatches the deploy workflow directly (`gh workflow run ... --ref main`, needs `actions: write` permission) rather than relying on the push trigger. If you add another workflow that commits/pushes and expects to cascade into a deploy, use the same explicit-dispatch pattern, not a bare push.
- **Don't schedule GitHub Actions cron triggers on the hour (`:00`).** GitHub's own docs warn that top-of-the-hour is the highest-load, most delay/drop-prone slot for `schedule` events. `update-vm-data.yml` originally used `0 5 * * *` and simply never fired (zero `schedule`-triggered runs recorded, only manual ones) — moved to `17 5 * * *`. If you ever add another scheduled workflow, pick an off-hour minute up front.
- **`az` CLI + PowerShell + Windows is quoting hell.** Inline JSON string arguments (e.g. `az ad app federated-credential create --parameters '{...}'`) get mangled by the `az.cmd` → `cmd.exe` re-parsing layer even when quoted correctly in PowerShell. Write the JSON to a temp file and pass the file path to `--parameters` instead of fighting quoting.
- **`dev` is the working branch, PRs target `main`.** The user prefers direct pushes to `main` once merged (not a review-gated flow) and daily automation (not weekly). PRs are opened as ready-for-review, not draft, unless told otherwise. Commit messages and PR bodies get a `Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>` trailer / "🤖 Generated with Claude Code" footer respectively.
- **Check for an existing open PR on `dev` before creating a new one** (`gh pr list --head dev --state open`) — it may already have been merged since you last looked, in which case a fresh one is needed instead of assuming the old one still tracks new commits.
